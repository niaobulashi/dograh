### 已核实的其余项
- 根 `.dockerignore` 没有排除 `ui/messages`（构建上下文是仓库根，`ui/.dockerignore` 不生效）✓
- `ui/package-lock.json` 里含 alpine 需要的 musl 变体（`@swc/core-linux-x64-musl`、`@parcel/watcher-linux-x64-musl` 等，共 86 处含 musl），`node:22-alpine` 的 `npm ci` 能装 ✓

## 本地 Postgres 直连（Navicat）信息与一个 pg_hba 坑

用户要用 Navicat 连本地 pg 库连不上。实测结论：`dograh-postgres-1` 端口 `0.0.0.0:5432->5432`，宿主 `127.0.0.1:5432` 可达（`/dev/tcp` 探测通过），Docker Desktop 29.7.2 / overlayfs。

连接信息：主机 `127.0.0.1`、端口 `5432`、用户 `postgres`、初始库 `postgres`（**库只有一个，没有单独的 dograh 库**）、SSL 关闭（容器 `ssl=off`）。密码取仓库根 `.env` 的 `POSTGRES_PASSWORD`（64 位随机串，非默认 postgres）。用户连不上多半就是密码填错了。

**坑：容器内测密码会假通过。** `pg_hba.conf` 有效行顺序是
```
local all all trust
host  all all 127.0.0.1/32 trust     <- 先匹配，直接放行不校验密码
host  all all ::1/128      trust
host  all all all          scram-sha-256   <- 只有网络来源才走这条
```
所以在容器里 `psql -h 127.0.0.1 -U postgres` 是 **trust、不验密码**，拿它验证 `.env` 密码是对不出来的。要真验密码，必须让来源 IP 落到最后的兜底规则，例如容器内 `psql "host=postgres ..."`（走 Docker 网络 IP）或从宿主经发布端口连。

## 【最终定论 + 修复】5432 端口被原生 PostgreSQL 18 抢占

上面那段"用户连不上多半是密码填错了"**结论是错的**，真根因如下（已实测修复）。

### 根因
宿主机 5432 上有**两个**监听进程（`netstat -ano | grep :5432`）：

| PID | 进程 | 身份 | 说明 |
|---|---|---|---|
| 8256 | `com.docker.backend` | Docker 端口代理 → dograh 容器 pg17 | 密码 = `.env` 的 hex |
| 7824 | `postgres.exe` | **原生 Windows 服务 `postgresql-x64-18`**（`E:\server\PostgreSQL\18`，`postgresql.conf` 里 `port = 5432`）| 另一个密码 |

Navicat / 宿主 psql 连 `127.0.0.1:5432` 实际命中的是**原生 PG 18**，不是容器 → 认证失败。
铁证：原生 PG 日志 `E:\server\PostgreSQL\18\data\log\postgresql-2026-10-10_085528.log` 里记着用户 17:33 那次 `用户 "postgres" Password 认证失败`，命中 `pg_hba.conf` line 115 `host all all 0.0.0.0/0 scram-sha-256`。

**密码本身没问题**：`7a06...09cc` 是明文（脚本随机生成的强密码，不是密文）。正确验证方式（走 Docker 网络 IP 才真正校验）：
```bash
docker exec -e PGPASSWORD=<hex> dograh-postgres-1 psql -h postgres -p 5432 -U postgres -d postgres -c "select 1;"   # 成功
docker exec dograh-api-1 printenv DATABASE_URL   # 里面就是这串 hex，api healthy 即密码正确
```

### 修复（已执行）
`docker-compose.override.yaml` 增加：
```yaml
services:
  postgres:
    ports: !override
      - "5433:5432"     # 5432 归原生 PG 18，Dograh 挪到 5433
```
`!override` 标签是必须的——Compose 对 `ports` 默认做**列表合并**，直接写会变成 5432+5433 两个映射。Compose v5.5.1 支持。
```bash
docker compose config | grep -A6 '^  postgres:'   # 校验 published: "5433"
docker compose up -d postgres                      # 只重建 pg 容器，数据卷 postgres_data 不受影响
```
验证：`psql -h 127.0.0.1 -p 5433 -U postgres` + hex 密码 → `17.11 ... postgres 29 张表` ✓；api `/api/v1/health` 200 ✓。

### 复用结论
> 本机装过原生 PostgreSQL（`E:\server\PostgreSQL\18`，服务名 `postgresql-x64-18`，端口 5432），**与 Docker 的 dograh pg 抢端口**。任何"宿主机连 5432 密码错、容器内却正常"的现象，先 `netstat -ano | grep :5432` 看是不是两个 PID。停服务用 `Stop-Service postgresql-x64-18`（需管理员），或把容器端口挪走（当前采用）。

## 修 api 镜像构建：OOM + 国内网络，已给 api/Dockerfile 打 4 处镜像源补丁

用户执行 `docker compose up -d --build ui api` 失败：
```
ERROR [api builder 3/8] RUN apt-get update && apt-get install -y git ...  411.7s
ResourceExhausted: ... did not complete successfully: cannot allocate memory
```
`Killed` + `cannot allocate memory` = build 容器被 OOM killer 干掉。

### 双因
1. **并发构建**：Compose v5.5.1 用 Bake **并行**构建 ui 和 api（日志里两个镜像同时 526.2s），Next.js 构建吃满内存，把同时跑 apt 的 api builder 拖死。
2. **apt 源慢**：日志 `Fetched 10.0 MB in 2min 0s (83.3 kB/s)`，还带一串 `Ign:` 重试。

### 实测数据（同一文件对比，这是换源的依据）
| 源 | 速度 |
|---|---|
| `deb.debian.org`（官方） | **20 kB/s** |
| `mirrors.tuna.tsinghua.edu.cn` | **1.02 MB/s**（约 50x） |
| `mirrors.aliyun.com` | 200 kB/s |
| `files.pythonhosted.org`（PyPI 官方） | **4.7 kB/s** |
| GitHub release（ffmpeg 包） | **55 kB/s** |
| `gh-proxy.com` 加速 | **1.06 MB/s** |
| `ghfast.top` 加速 | 0.93 MB/s |
| `registry.npmjs.org` | 190 kB/s（尚可） |

### 已改的 4 处（`api/Dockerfile`，均标注 `LOCAL PATCH (国内网络)`，回退用 `git checkout api/Dockerfile`）
1. **builder 阶段 apt 换清华源**（加一行 sed 替换 `/etc/apt/sources.list.d/debian.sources` 里的 `deb.debian.org`）。
2. **uv 换清华 PyPI**：`ENV UV_DEFAULT_INDEX` + `UV_INDEX_URL` + `UV_HTTP_TIMEOUT=120`。
3. **ts-deps 阶段 npm** → `registry.npmmirror.com`。
4. **ffmpeg-static 阶段**：apt 同 1；下载改成**镜像轮询** `gh-proxy.com` → `ghfast.top` → GitHub 直连，逐源过 sha256（校验不过就换下一个源），`--max-time` 600→900。
   → 理由：GitHub 直连 55 kB/s，35MB 的包在 600s 内根本拉不完，`--retry 3` 也救不回来。sha256 是钉死的，走第三方源不影响供应链安全。

### 验证方式与结果（都实跑过）
```bash
# 1) 全部 RUN 指令 shell 语法校验 —— 用 python 把 Dockerfile 的 RUN 还原成脚本喂 sh -n
#    → 8/8 通过
# 2) sed 在 /etc/apt/sources.list 不存在时是否仍改写 debian.sources → URIs 已变 tuna ✓
# 3) 实跑 builder 层：sed + apt-get install git → 44 秒装好 git 2.47.3（之前 412s 被杀）
# 4) 实跑 ffmpeg 层：sed + apt + 下载 + sha256 + 解包 → 首次命中 gh-proxy，sha256 OK，
#    总耗时 3m10s，二进制版本 N-124714-g49a77d37be-20260531 与 BTBN_REV 一致 ✓
# 5) uv 索引：uv 0.13.0 同时设两个变量，pip compile 命中 pypi.tuna 6 次、无 deprecation 警告 ✓
```

### 踩坑备注
- `uv` 官方镜像是 **distroless**：没有 `sh`、没有 `/tmp`、`uv` 在 `/uv` 不在 PATH（`COPY --from=... /uv` 才拿得到）。想验证得 `docker create` + `docker cp` 把二进制抠出来塞进 `python:3.13-slim` 跑；直接 `docker run --entrypoint sh` 会报 `executable file not found`。
- 两个基础镜像（`python:3.13-slim` / `debian:trixie-slim`）在 trixie 上**都只有 `/etc/apt/sources.list.d/debian.sources`（deb822 格式），没有 `/etc/apt/sources.list`**。sed 要两个文件都带上并 `|| true`，GNU sed 会先改存在的那个再报第二个不存在。
- `docker buildx du --verbose` 能看到每个 cache 记录的 Description 和 Size，配合 `awk` 可以判断某一层（如 ffmpeg-static）到底缓存没缓存。
- **别 `docker builder prune`**：会连 ffmpeg-static 那层缓存一起清掉，反而逼着重新下载 GitHub 的包。
