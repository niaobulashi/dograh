## DeepSeek key invalid 排查（create/template 报 authentication_error）
- 现象：`[create/template] MPS/LLM HTTP error ... api key: ****21cc is invalid`。
- 根因：**不是 key 本身失效，是 api 容器还带着旧 env**。`.env` 里 `DEEPSEEK_API_KEY` 已换成 ...10f0（实测直连 HTTP 200），但容器 env 仍是 ...21cc。`docker compose restart` 不会重读 .env，必须 `up -d` 触发 recreate。
- 修复/验证：`docker compose --profile tunnel up -d api`（**无需 --build**，key 由 compose environment 运行时注入）→ `docker inspect dograh-api-1 ... | grep DEEPSEEK_API_KEY` 尾号变 10f0 → 容器内 python urllib 实调 chat/completions 得 HTTP 200。
- 关键事实：模板生成走 `WORKFLOW_TEMPLATE_GENERATOR=local` → `api/services/workflow/local_template_generator.py`，key 在 `api/constants.py:84` 于 import 时读一次 `os.getenv`，故必须重启进程。

## create/template 500：DetachedInstanceError（create_workflow 返回已过期对象）
- 现象：DeepSeek 生成成功后 `Instance <WorkflowModel> is not bound to a Session; attribute refresh operation cannot proceed`，接口 500。
- 根因：`api/db/workflow_client.py:create_workflow` 里 `await session.commit()` 后直接 `return new_workflow`。`async_sessionmaker` 默认 `expire_on_commit=True`，commit 把全部属性置为 expired，`async with` 退出又关闭 session → 路由层第一次读 `workflow.id` 就触发 refresh → 对象已 detached。原代码在 `raise e` 之后还有一行 `await session.refresh(new_workflow)`，是不可达死代码，等于从未刷新过。
- 影响面：所有调用 `create_workflow` 的路径（workflow.py:518 直接创建、658 create/template、1752、services/workflow/duplicate.py:79 复制 Agent、mcp_server/tools/create_workflow.py）。此前一直被 DeepSeek key 报错挡在前面，才没暴露。
- 修复：commit 前先取 `workflow_id = new_workflow.id`；commit 后在 session 内 `session.get(WorkflowModel, workflow_id, options=[selectinload(current_definition), selectinload(released_definition)], populate_existing=True)` 重新加载再返回（与 `get_workflow` 的 eager load 保持一致），并删掉 `raise e` 后的死代码。副作用修正：`current_definition_id` 由 None 变为真实 id。
- 验证（不 build，直接 docker cp 两份文件进容器 + restart 后跑探针）：属性全部可读，`current_definition_id=13`、`released_definition.version_number=1`，探针数据 `delete_workflow` 清理成功。容器内为临时热补丁，需 `docker compose --profile tunnel up -d --build api` 固化。
- 坑：Git Bash 下 `docker compose exec ... python /tmp/x.py` 会被 MSYS 改写成 `C:/...`，需 `MSYS_NO_PATHCONV=1`。

## 画布「没收集信息就挂断」根因与改造方案
- 方案文档 `doc/家电维修画布-信息收集改造.md` + 可直接参考的画布 `doc/家电维修画布-改造后.json`（6 节点：startCall → 故障判断 → 预约收集 → 复述确认 → 成功/婉拒双 endCall + globalNode）。
- 机制事实（后续回答类似问题可直接引用）：
  1. 节点出边 = LLM 工具；函数名取 `edge.label` 经 `transition_tool_name`（`workflow_graph.py:20`，非 a-z0-9 全换 `_`），描述取 `edge.condition`（`pipecat_engine_context_composer.py:135-139`），节点激活时注册（`pipecat_engine.py:839-847`）。→ **中文 label 会变成 `____`**，同节点两条中文边直接校验失败。
  2. 画布不是状态机，LLM 每轮自主决定调哪条边；condition 模糊（"完成后结束"）必被提前调 → 进 endCall 播完即挂（`pipecat_engine.py:472-491`）。
  3. `extraction_variables` 只在「转节点前」和「通话结束时」各跑一次，**不驱动追问、不阻止挂断**。
  4. `transition_speech` 不渲染模板变量（`pipecat_engine.py:464-465` 纯文本入 TTS），要念信息得放节点 prompt 里。
  5. 节点 prompt 拿不到 `gathered_context`（`_call_context_vars` 只有 initial_context + runtime_configuration），别在 prompt 里写 `{{gathered_context.xxx}}`。
- 生成器源头问题：`local_template_generator.py:169-170` 硬编码 startCall→agentNode→endCall 单 agentNode；`:179` 要求 label 也翻译成目标语言 → 工具名变下划线；`:160` 未要求 ASCII label。已给出补充提示词建议（label 强制 ASCII、收集类任务单独开节点）。

## start_docker.ps1 拉镜像失败（docker.io 直连不通）
- 现象：`docker compose --profile tunnel up --pull always` 全部 Interrupted，`dial tcp registry-1.docker.io:443` 超时；且 `No such image: dograh-api:local / dograh-ui:local`。
- 两个叠加根因：① Docker Desktop 无 registry-mirrors、无代理，国内直连 docker.io 必挂（2026-10-17 实测：docker.1ms.run 401 可用、ghcr.1ms.run 401 可用、docker.m.daocloud.io 502、docker.xuanyuan.me 死）；② `--pull always` 会连 build 型镜像 dograh-api:local/ui:local 也去 docker.io 拉（本地不存在），本地自建场景根本不该用官方脚本的这条命令，应 `docker compose --profile tunnel up -d --build`。
- registry-mirrors 只覆盖 docker.io，不覆盖 ghcr.io；ghcr 拉不动时用 `ghcr.1ms.run` 换源 retag（前提：up 时不带 --pull always，本地已有该 tag 则不会强拉）。
