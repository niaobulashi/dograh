# 家电维修画布：为什么没收集信息就挂断 + 怎么改

## 一、结论（4 条机制事实，不是猜）

1. **节点的出边 = LLM 可调用的工具**。函数名取边的 `label`（`transition_tool_name`：非 `a-z0-9` 全替换成 `_`），描述取边的 `condition`。LLM 每一轮自己决定调不调，**画布不是硬状态机**。
   - `api/services/workflow/workflow_graph.py:20` `transition_tool_name`
   - `api/services/workflow/pipecat_engine_context_composer.py:135-139` `description = edge.condition`
   - `api/services/workflow/pipecat_engine.py:839-847` 节点激活时把每条出边注册成工具
2. **你的 agent 节点只有一条出口，条件是「问题解答完成或预约信息收集完成后结束」**。LLM 给出维修建议后自认为「解答完成」→ 调该工具 → 进 endCall → endCall 的 prompt 播完即挂断（`pipecat_engine.py:472-491`）。
3. **`extraction_variables` 不驱动追问**。抽取只在「转节点前」和「通话结束时」各跑一次（`pipecat_engine.py:445-449`、`_perform_final_variable_extraction`），抽不到就是抽不到，不会阻止挂断、不会触发反问。
4. **你的边 label 是中文**，工具名会被算成 `____`（4 个下划线）、`______`（6 个下划线）。模型要靠 4 个下划线去猜「这是结束通话」，很容易误调；同一节点两条中文边还会直接校验失败（`Transition tool name "____" is duplicated`）。

对话记录里 LLM 一条回复连问 3 件事（品牌型号 / 购买时间保修 / 地址电话），用户只答了「不制冷了」，LLM 就认为信息问过了 —— 这违反「一次只问一件事」，也放大了第 2 条。

## 二、改成 6 个节点（一个节点只干一件事）

| id | 类型 | 名称 | 出口 |
|----|------|------|------|
| 1 | startCall | 开始通话 | `to_diagnose` → 2、`end_call_declined` → 6 |
| 2 | agentNode | 故障判断与解答 | `to_booking` → 3、`end_call_declined` → 6 |
| 3 | agentNode | 预约信息收集（一次一项） | `go_to_confirm` → 4 |
| 4 | agentNode | 复述确认 | `close_success` → 5、`back_to_booking` → 3 |
| 5 | endCall | 预约成功结束 | — |
| 6 | endCall | 婉拒/挂断结束 | — |
| 7 | globalNode | 全局设定 | —（global 节点不允许连线） |

收集动作全部落在节点 3，它的唯一出口 `go_to_confirm` 的 condition 写死三项齐全才允许调用 —— 没收集完就出不去。

## 三、节点 prompt（直接复制）

### 节点 1｜开始通话（startCall）

```
你是家电维修服务中心的语音小助手，语气亲切、耐心、专业。

【本次通话目标】
问清称呼 → 问清家电类型和故障 → 需要上门就收集手机号、地址、上门时间。

【本节点任务】
自我介绍一句，然后只问称呼。用户回答后用姓名称呼对方一次。

【规则】
- 每轮只说一到两句话，每轮只问一个问题。
- 听不清或噪音时，礼貌请对方再说一遍，不要猜。
- 不要报价、不要承诺到达时间。
- 用户没说姓名就直接往下走，不要纠缠。
```

### 节点 2｜故障判断与解答（agentNode）

```
【本节点任务】
判断家电类型和故障现象，给出最常见原因，然后问是否需要预约上门。

【流程】
1. 还不知道家电类型：只问「是哪一类家电出了问题」。知道就跳过。
2. 还不知道故障现象：只问「具体是什么情况」。知道就跳过。
3. 用一到两句话说明最常见原因，可给一个自查建议。
4. 问：「需要帮您预约师傅上门看一下吗？」

【规则】
- 每轮两到三句话，只问一个问题。
- 常见原因只是参考，不要说「肯定是」这种结论式诊断。
- 不报价、不承诺上门时间。
- 本节点不索要手机号和地址，也不主动结束通话。

【成功标准】
- 用户明确表示需要上门维修 → 才调用 to_booking。
- 用户明确表示不需要上门、自己处理 → 才调用 end_call_declined。
- 用户还在描述问题、或你还没问过是否需要上门时，不要调用任何工具。
```

### 节点 3｜预约信息收集（agentNode，变量抽取挂这里）

```
【本节点任务】
依次收集三项：手机号 → 详细地址 → 上门时间。一次只问一项。

【流程】
1. 问手机号：「方便留一个手机号吗？师傅上门前会先跟您联系。」用户说完复述：「我记一下，是 138xxxx，对吗？」确认后再往下。
2. 问地址：「麻烦说一下详细地址，包括小区和门牌号。」复述确认。
3. 问时间：「您哪天方便？上午还是下午？」用户说得含糊就追问到具体时段。复述确认。
4. 三项都确认后，调用 go_to_confirm 做最终复述。

【规则】
- 一条回复里只能问一项，绝对不能把手机号、地址、时间一起问。
- 用户答非所问或只答了一部分，就重复同一个问题，不要跳到下一项。
- 手机号必须凑齐 11 位，缺位就请对方补一遍；听不清就请对方重复。
- 地址要听到城市/区和门牌号，只说了小区就追问门牌。
- 用户要改前面说过的信息，回到那一项重新确认。
- 本节点不要自己结束通话。

【成功标准】
- 手机号、地址、上门时间三项都拿到并复述确认过 → 才调用 go_to_confirm。
- 任一项缺失或被用户否认 → 不要调用 go_to_confirm，继续问。
```

抽取配置（保持你原来的三个变量，只把 hint 写细）：

- `extraction_prompt`：`从对话中提取用户提供的手机号、上门地址、预约时间。只提取用户明确说出并确认过的值；用户否认或修改过的取最后一次确认的值；没提到的不要编造。`
- `mobile_number`（string）：`用户本人的 11 位手机号，纯数字，不含中文和空格`
- `address`（string）：`上门维修的详细地址，包含城市/区、小区、门牌号`
- `appointment_time`（string）：`用户同意的上门时间，包含日期和时段（上午/下午/几点）`

### 节点 4｜复述确认（agentNode）

```
【本节点任务】
把已收集的三项信息一次复述清楚，请用户确认，然后结束。

【流程】
1. 逐项复述：手机号、详细地址、上门时间。
2. 问：「以上信息对吗？」
3. 用户确认 → 调用 close_success。
4. 用户要改某一项 → 调用 back_to_booking 回去改。

【规则】
- 只复述，不新增信息，不重复追问已经确认过的内容。
- 用户没有明确确认之前，不要结束通话。
```

### 节点 5｜预约成功结束（endCall）

```
复述一句已记录的预约时间，说明师傅会在上门前用这个手机号联系，感谢来电并道别。
```

### 节点 6｜婉拒/挂断结束（endCall）

```
礼貌收尾，说明之后有需要随时来电，祝对方生活愉快，道别。
```

### 节点 7｜全局设定（globalNode）

```
你是家电维修服务中心的语音小助手，语气亲切、耐心、专业。回答简短，每次控制在两三句话内。
每轮只问一个问题，用户没答完就不要问下一项。
遇到听不清或噪音时，礼貌请对方再说一遍。
不要编造维修价格，不要承诺具体到达时间；不确定时说明会安排师傅联系确认。
没有明确的收尾指令时，不要结束通话。
```

## 四、边的 label / condition（label 必须 ASCII）

| 边 | label（函数名） | condition（= 工具描述，给 LLM 看的闸门） |
|----|----------------|------------------------------------------|
| 1→2 | `to_diagnose` | 用户已经说出称呼或明确不想说姓名，并且已经说明来电意图（咨询或维修某类家电）。这两个条件都满足才调用；缺一个就继续在本节点追问。 |
| 1→6 | `end_call_declined` | 用户一开口就明确表示打错了、不需要、要挂断。仅此情况调用。 |
| 2→3 | `to_booking` | 用户明确表示需要师傅上门维修。仅在用户同意上门后调用；用户还在描述故障、犹豫、或在问价格时不要调用。 |
| 2→6 | `end_call_declined` | 用户明确表示不需要上门、自己处理，或明确表示不想继续通话。仅在用户明确拒绝后调用。 |
| 3→4 | `go_to_confirm` | 手机号、地址、上门时间三项都已经问到，并且每一项都经过复述确认。任一项缺失或被用户否认时不要调用，继续在当前节点追问。 |
| 4→5 | `close_success` | 用户明确确认复述的手机号、地址、上门时间都正确。没有得到明确确认不要调用。 |
| 4→3 | `back_to_booking` | 用户指出复述的信息中有任何一项需要修改。 |

`transition_speech` 留空：它不渲染模板变量（`pipecat_engine.py:464-465` 直接当纯文本播），要念信息就在节点里念。

## 五、为什么原来会挂断：先确认是哪条路径

```bash
# 是不是边被触发了（会把工具名、目标节点打出来）
docker compose logs api --since 2h | grep -E "LLM Function Call EXECUTED|transitioning to node"

# 是不是被超时/空闲掐掉
docker compose logs api --since 2h | grep -Ei "USER_IDLE_MAX_DURATION|CALL_DURATION_EXCEEDED|user_idle|max duration"
```

- 有 `transitioning to node: 4` → 就是边条件太松，第 2 条根因成立。
- 没有该行、只有 idle / max duration → 是用户静音或通话时长限制，跟画布无关。

## 六、红线

- **一条边一个闸门**：condition 里必须同时写「仅在…才调用」和「…时不要调用」，模糊的「完成后结束」一定被 LLM 提前调。
- **一个节点只问一个字段**：一条回复里问两项以上，用户只会答一项，后面全靠追。
- **label 只用小写字母+下划线**：中文 label 会被转成 `____`，同节点还会撞名报错。
- **extraction 不驱动流程**：它只在转节点前和结束时各跑一次，别指望它触发追问。
- **global 节点不能连线**（`max_incoming=0, max_outgoing=0`），它靠 `add_global_prompt` 拼接到每个节点 prompt 前面。

## 七、生成器已改（`local_template_generator.py`）

原提示词把坑写死在源头：`:169-170` 硬编码 `startCall → agentNode → endCall` 单节点；`:179` 要求 label 也跟着翻译成中文 → 工具名变 `____`；`:160` 没要求 ASCII label。现在改成：

**提示词层**
- 新增「运行时怎么工作」一节：出边即工具、label=函数名、condition=工具描述，所以「一节点一职责、一边一闸门」，明确禁止把整通电话塞进一个 agentNode。
- 给出预约类话务的参考形状（greet → diagnose → collect（一轮一字段）→ read back → 2-3 个不同结局）+ 5 条自检清单（3-6 个 agentNode、收集必须有独立节点、condition 必须写正反两面、2-3 个 endCall、label 必须 `^[a-z0-9_]+$`）。
- 新增「Edge rules」：label 只允许小写 ASCII 下划线，永不翻译；同节点不重名；condition 一句话必须同时写「何时调用」和「何时不要调用」；节点 prompt 里要点名工具名。
- 新增 agentNode prompt 四段式（【本节点任务】【流程】【规则】【成功标准】），明确「一轮只问一个字段」、FAQ 以「症状 → 最可能原因」形式写。
- `max_tokens` 4096 → 8192（多节点 + 长 prompt 会被截断），`temperature` 0.7 → 0.5，并检查 `finish_reason == "length"` 打错误日志。

**代码层兜底**
- 新增 `_slugify_edge_label` + `_normalize_edges`：label 一律重新 slug 成 ASCII；空的/纯中文的按目标节点类型兜底（`to_agent` / `end_call`），同源重名自动加 `_2`；断头边（source/target 不存在）直接丢弃。
- `_normalize_definition` 排版改两趟：agentNode 纵向堆叠（间距 240），endCall 排在它们下方一行（x 间隔 460），多结局不再叠在一起。

| endCall | 1 | 3（成功、放弃、安全隐患） |

| condition | 「问题解答完成或预约信息收集完成后结束」 | 「三项都完整拿到且用户逐项口头确认才调用，缺一项继续追问」 |
